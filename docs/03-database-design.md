# 3. Database Design

## Overview

The Consent Manager stores all consent-related information in a PostgreSQL database using Prisma ORM.

The database is designed around two core principles:

- Maintain the current consent state for every user.
- Maintain a complete audit trail of every consent-related action.

The current prototype consists of two primary tables:

- **Consent**
- **AuditLog**

---

> **Note**

> There is currently no foreign key relationship between the two tables.
> AuditLog records are immutable historical events generated by business operations rather than child entities of a Consent record.

# Consent Table

The Consent table stores the **current consent state** for each user.

Each record represents one consent purpose for one user within one tenant.

Example:

```text
Tenant
amazon

User
user-123

Purpose
marketing

Status
GRANTED
```

---

## Prisma Model

```prisma
model Consent {
  id            String        @id @default(cuid())

  tenantId      String

  userId        String

  purpose       String

  status        ConsentStatus

  policyVersion String

  createdAt     DateTime      @default(now())

  @@index([tenantId])
  @@index([userId])
  @@index([purpose])

  @@index([tenantId, userId])

  @@index([tenantId, userId, purpose])

  @@unique([tenantId, userId, purpose])
}
```

---

## Fields

| Field | Type | Description |
|--------|------|-------------|
| id | String | Unique consent identifier |
| tenantId | String | Organization identifier |
| userId | String | User identifier |
| purpose | String | Purpose for processing data |
| status | Enum | Current consent status |
| policyVersion | String | Version of accepted privacy policy |
| createdAt | DateTime | Consent creation timestamp |

---

# Consent Status

The system currently supports two consent states.

| Status | Description |
|---------|-------------|
| GRANTED | User has granted consent |
| REVOKED | User has withdrawn consent |

Prisma Enum

```prisma
enum ConsentStatus {
  GRANTED
  REVOKED
}
```

---

# Composite Unique Constraint

```prisma
@@unique([tenantId, userId, purpose])
```

This constraint ensures that there can only be one current consent record for a given:

- Tenant
- User
- Purpose

Example

Valid

```text
amazon

user-123

marketing
```

Invalid

```text
amazon

user-123

marketing

(second record)
```

Instead of creating duplicates, the application updates the existing consent record.

# AuditLog Table

The AuditLog table records every significant consent-related action performed by the system.

Unlike the Consent table, AuditLog records are never modified.

Each entry represents a historical event.

---

## Prisma Model

```prisma
model AuditLog {
  id         String   @id @default(cuid())

  tenantId   String

  userId     String

  action     String

  purpose    String?

  metadata   Json?

  createdAt  DateTime @default(now())

  @@index([tenantId])

  @@index([userId])
}
```

---

## Fields

| Field | Type | Description |
|--------|------|-------------|
| id | String | Audit record identifier |
| tenantId | String | Organization identifier |
| userId | String | User identifier |
| action | String | Performed action |
| purpose | String | Consent purpose |
| metadata | Json | Additional event metadata |
| createdAt | DateTime | Event timestamp |

# Why Separate Consent and AuditLog?

The project intentionally separates current state from historical events.

---

## Consent

Represents:

```text
Current Truth
```

Example

```text
Marketing

GRANTED
```

---

## AuditLog

Represents

```text
History
```

Example

```text
12:30

CONSENT_GRANTED

↓

12:45

CONSENT_REVOKED
```

---

Benefits

- Faster permission verification
- Simpler queries
- Complete audit history
- Immutable event records

# Multi-Tenant Design

Every record contains a tenant identifier.

Example

```text
Tenant A

user-123

marketing
```

```text
Tenant B

user-123

marketing
```

Although both records reference the same user identifier, they belong to different organizations and remain completely isolated.

Every service query filters by tenant.

Example

```typescript
where: {
    tenantId,
    userId,
    purpose
}
```

---

```text

userId

purpose

status = GRANTED
```

---

## Fetch User Consents

```text
SELECT

WHERE

tenantId

userId
```

---

## Revoke Consent

```text
UPDATE

Consent

↓

INSERT

AuditLog
```

---

## Fetch Audit Logs

```text
SELECT

FROM AuditLog

WHERE

tenantId

userId

ORDER BY createdAt DESC
```

---

# Transaction Design

Operations affecting multiple tables are executed within a single Prisma transaction.

Example

Grant Consent

```text
BEGIN

↓

Insert Consent

↓

Insert AuditLog

↓

COMMIT
```

If any operation fails

```text
ROLLBACK
```

This guarantees consistency between Consent and AuditLog.

# Summary

The current database design provides:

- Multi-tenant data isolation
- Current consent state
- Immutable audit history
- Efficient consent verification
- Indexed lookup operations
- Transactional consistency

This schema forms the foundation of the Consent Manager and is intentionally designed to support future enhancements such as policy engines, SDK integration, API authentication, and event-driven consent workflows without requiring significant structural changes.
